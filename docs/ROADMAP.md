# mplan 优化路线图（讨论稿）

> 最后更新：2026-11-07
> 这是建议清单，不是承诺。优先级需要结合团队实际痛点再定。

## 一、当前基线

- 已完成：4 层任务树、甘特拖拽、工时/日期联动、公司日历、里程碑、筛选、CSV 导入导出、变更日志、撤销。
- 已完成：匿名只读 + 成员按项目授权 + 管理员账号/人员/日历管理。
- 已完成：自托管发布脚本（systemd + Docker nginx + 已有 MySQL），发布不写演示数据。
- 待处理：自托管默认是 HTTP，HA 需要域名 + TLS；生产环境仍建议加反向代理。
- 工程现状：已有 Git / GitHub Actions / core 单测；还没有 API 与 UI 自动化集成测试，也没有 migration 文件。

## 二、优先级建议

### P0：让生产环境可靠（优先于新功能）

| # | 事项 | 要解决的问题 | 工作量 | 风险 |
|---|---|---|---|---|
| 1 | 域名 + HTTPS | 自托管默认 HTTP；绑域名、配 TLS，`COOKIE_SECURE=1` | S–M | 低 |
| 2 | 自动备份与恢复演练 | 现在只有手工 `mysqldump`；需要定时备份 + 保留策略 + 实际恢复一次 | S | 低 |
| 3 | 发布可回滚 | 当前 rsync 原地覆盖，没有历史版本；改成 `releases/<timestamp>` + `current` 软链，保留最近 N 版 | M | 中 |
| 4 | 数据库 migration | `drizzle-kit push` 删列/改类型可能丢数据；切到 `generate + migrate`，发布时先迁移再启动 | M | 中 |
| 5 | 管理员密码生命周期 | 初始密码目前存在 `.deploy.env`；增加首次登录强制改密、自助改密、重置后强制下线提示 | S–M | 低 |
| 6 | 监控与日志 | journald 日志无限增长；没有 uptime/磁盘/MySQL 告警；接飞书/钉钉 webhook 或简单探活 | S | 低 |

> 建议顺序：1 → 2 → 3 → 4 → 5 → 6。当前已经能跑，先把「丢了能不能恢复、坏了能不能回滚」补齐。

### P1：让日常使用更顺

| # | 事项 | 价值 | 工作量 | 备注 |
|---|---|---|---|---|
| 7 | 项目设置 UI | 目前只能新建/删除，不能改名称、编号、计划日期、备注；也没有归档 | S | 复用现有 PATCH `/api/projects/:id` |
| 8 | 通知 / 提醒 | 逾期、今天到期、被分配新任务时通知到人；飞书/钉钉群机器人最省事 | M | 先做每日 digest，不做实时推送 |

## 三、我的建议

如果目标是「团队马上日常用起来」，建议先做：

1. **P0 的 1–4**：域名 + HTTPS、备份、可回滚发布、migration。这些是上线后的安全网。
2. **P1 的 7 + 8 + 9**：项目设置、通知、我的任务。这三项最直接减少「每天打开系统找任务」的成本。
3. 移动端只读和甘特截图放到下一轮；任务依赖、实时协作暂时不做。

如果团队目前只有 3–5 人、项目数 < 10，可以跳过 #9 的跨项目 dashboard，优先做 #7 和 #8。

## 四、需要一起确认的问题

1. 团队规模和使用频率：每天多人同时编辑，还是项目经理单人维护、其他人只看？
2. 通知渠道：飞书、钉钉、企业微信、邮件，还是先站内提示即可？
3. 是否有明确的域名/证书？继续用 IP + 端口，还是挂到反向代理 / 域名下？
4. 权限要不要细到「任务负责人」？现在项目级授权是否够用？
5. 手机端是「能看即可」，还是需要完成状态、改日期等轻量编辑？
6. 任务依赖是真实痛点，还是只是「看起来更专业」？如果要做，接受只读依赖线 + 手工顺延吗？
7. 发布频率：每周一次还是每天多次？这决定是否值得做 releases/回滚和 CI。
8. 数据重要程度：丢失一天的排期数据是否可以接受？这决定备份和恢复演练的投入。
